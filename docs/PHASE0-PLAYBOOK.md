# Phase 0 Playbook — реверс протокола Devast.io

Цель фазы: превратить сырые WebSocket-кадры в версионируемую схему, достаточную для headless-бота. Это не «собрать пакеты и угадать»: каждый подтверждённый опкод проходит цепочку **захват → корреляция → гипотеза → воспроизведение → фикстура**.

## 1. Подготовка

1. `npm install && npm run build`.
2. `npm run recorder` — приёмник на `127.0.0.1:8787`, сессии в `./sessions`.
3. Установить `tools/sniffer/master-client-sniffer.user.js` в Tampermonkey.
4. Открыть Devast.io, убедиться в консоли: `[devast-tap] transport ready` и периодический `[devast-tap] in/out N`.
5. Если статуса нет — проверить:
   - Tampermonkey включён для домена;
   - вкладка не в фоновом режиме сна;
   - игра не использует Web Worker для сети (тогда tap не увидит трафик — зафиксировать как открытый вопрос).

## 2. Захват сессии

План сессии (минимум 10):

| # | Что делать | Что ищем |
|---|---|---|
| 1 | Только зайти в мир, постоять | handshake, keepalive, спавн, начальный инвентарь |
| 2 | Ходить по 4 направлениям, по диагонали | move, направление/скорость, частота |
| 3 | Добыть дерево/камень/руду разными инструментами | gather/start/stop, смена инструмента |
| 4 | Скрафтить предмет, открыть верстак | inventory, craft, UI-опкоды |
| 5 | Построить стену, сломать | build, destroy, обновление структур |
| 6 | Согреться, зайти в рад-зону | temperature/radiation, survival-статы |
| 7 | Атаковать моба, получить урон | attack, hit, death |
| 8 | Умереть и респавниться | death/respawn, сброс инвентаря |
| 9 | Дисконнект/реконнект | reconnect-handshake |
| 10 | Чат, лидерборд, миникарта | text-опкоды, leaderboard sync |
| 11 | Собрать еду (ягоды/мясо/грибы), съесть | food/gather, eat/use-item |
| 12 | Принять антирадин/бинт/аптечку, использовать бафф | heal/buff, inventory use, cooldown |
| 13 | Спринт (Shift+W) до ~50%, остановка, реген | stamina drain/regen, скорость, порог 50% |
| 14 | Бой на низкой стамине: рывок → атака → отход | stamina в бою, cadence, regen |
| 15 | Отход домой от темноты/гулей на полной стамине | emergency-retreat, drain ниже 50% |

Перед каждым действием ставить метку:

```js
window.__devastTap.mark("axe-on-tree")
```

Метка попадёт в `actions.jsonl` с timestamp и позволит связать её с исходящими кадрами. Без меток корреляция по одним кликам работает хуже: между нажатием и пакетом есть задержка кадра/анимации.

При live-захвате через CDP (`tools/recorder/cdp-live.mjs`) actions.jsonl нет — только сетевые кадры. Делай одно действие за 1–2 секунды с паузой, чтобы пакеты еды/лекарств/баффов не слипались.

## 3. Первичный анализ

```bash
node tools/recorder/analyze.mjs sessions/<dir>
# черновик схемы: opcode offset 0/u8, пустые поля, status=hypothesis
node tools/recorder/analyze.mjs sessions/<dir> --emit-schema
```

Смотреть по порядку:

1. **Фрейминг.** Все кадры кратны длине сообщения WS? Первый байт — опкод? Есть ли length-prefix? Если длины скачут и первый байт стабилен — гипотеза `u8 opcode`.
2. **Распределение длин.** Фиксированные длины (4/8/12/16) — кандидаты на простые команды (move, ping). Переменные — текст/инвентарь.
3. **Корреляция действий.** Таблица «действие → firstByte → length» в `report.md`: если `keydown W` стабильно даёт кадр длины 9 с опкодом `0x0e` — это move.
4. **Направление.** `in` и `out` анализируются раздельно; опкод `0x01` в разных направлениях — разные пакеты.
5. **Энтропия.** Высокая энтропия + переменная длина — сжатие/шифрование; низкая — структура.

## 3a. Текстовые JSON-кадры

Если кадр — WebSocket-text и начинается с `[`, это JSON-массив с опкодом в индексе 0. Не пытайтесь описывать его байтовыми смещениями: для него в `config/protocol-schema.json` есть секция `textOpcodes`.

Первый захват дал:

| opcode | Наблюдаемая форма | Гипотеза |
|---:|---|---|
| 1 | `[1,33,31760,"Desert Eagle",0,0]` | kill/death-событие с оружием (гипотеза; наблюдалось возле Game Over) |
| 2 | `[2,0,name,...,token]` | roster/список игроков |
| 5 | `[5,tag,0,tag,...]` | клан-теги сервера |
| 6 | `[6,n,n]` | пара чисел |
| 7 | `[7,id,id,...]` | список ID |
| 8 | `[8,id,name,n]` | id/name/value |
| 9 | `[9,id,name,flag,...]` | leaderboard |

Правило: `status: "hypothesis"` до подтверждения семантики на 3+ сессиях. Обезличенная фикстура — `fixtures/captured-frankfurt4/`.

## 4. Гипотеза → подтверждение

Для каждого кандидата:

1. Записать `hex` кадра и контекст (действие, время, соседние кадры).
2. Составить гипотезу полей: например, `x: f32le @1`, `z: f32le @5`.
3. Проверить на 3+ независимых сессиях: одинаковое действие → одинаковое смещение и правдоподобные значения.
4. Проверить диапазоны: координаты в пределах карты, скорость < разумного максимума, HP 0..100.
5. Только после этого — `status: "confirmed"` и осмысленное имя.
6. Добавить кадр в `fixtures/<name>/frames.jsonl`, сгенерировать `expected.json` через `npm run fixtures:update`, проверить diff глазами.

Правило: **одно наблюдение — не подтверждение.** Опкод, который встретился один раз и «похож на движение», остаётся `hypothesis`.

## 5. Обновление схемы

`config/protocol-schema.json`:

```json
{
  "schemaVersion": 2,
  "game": "devast.io",
  "gameBuild": "2026-11-11",
  "capturedAt": "2026-11-11T12:00:00Z",
  "authoritative": true,
  "framing": { "mode": "ws-message" },
  "opcodes": {
    "c2s": {
      "0x0e": {
        "name": "move",
        "direction": "c2s",
        "status": "confirmed",
        "opcode": { "offset": 0, "type": "u8" },
        "fields": [
          { "name": "x", "offset": 1, "type": "f32le" },
          { "name": "z", "offset": 5, "type": "f32le" },
          { "name": "flags", "offset": 9, "type": "u8" }
        ]
      }
    },
    "s2c": {}
  },
  "unknownOpcodes": []
}
```

Правила версионирования:

- `schemaVersion` — при изменении трактовки полей.
- `gameBuild` — при обновлении клиента игры.
- Старые фикстуры не удаляются: они привязаны к `gameBuild` и проверяют, что новый парсер не сломал старый формат (или явно помечают несовместимость).

## 6. Проверка после обновления игры

1. `npm run fixtures:check` — старые фикстуры должны проходить или явно падать с указанием несовместимости.
2. Захватить короткую сессию, прогнать `analyze`.
3. Посчитать `unknown_rate`: доля кадров без схемы. Порог тревоги — 5% (I3/§13).
4. При росте unknown — остановить боевые приказы, обновить схему, только потом возобновлять.

## 7. Гигиена данных

- `sessions/` в `.gitignore`; реальные ники и IP не публиковать.
- Для фикстур обезличивать: ник → `player_1`, клан → `clan_x`, но байты координат/опкодов не менять, иначе фикстура теряет смысл.
- Не логировать handshake-заголовки с токенами/cookies. Sniffer пишет только URL без query.

## 8. Критерий выхода из Phase 0

- [ ] ≥10 сессий, покрывающих таблицу §2.
- [ ] Подтверждены: handshake, keepalive, move, gather, inventory, attack, death/respawn.
- [ ] `fixtures:check --strict` зелёный на подтверждённых кадрах.
- [ ] `unknown_rate < 5%` на живой сессии.
- [ ] Схема содержит `gameBuild` и привязана к фикстурам.
- [ ] Документированы частота пакетов, средний/пиковый размер, поведение при реконнекте.

После этого — Phase 1: один headless-бот, read-only проверка мира, без боя.
